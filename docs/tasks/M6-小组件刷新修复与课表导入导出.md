> 布局侧不用改数值——它们只引用 drawable。**但要确认两个布局都还引用 `@drawable/widget_bg_rounded`**：若某处写死了裸色值或别的 drawable，圆角改动就不会生效（M4-W 曾因 loading 态漏改而出现「加载方角 → 内容圆角」跳变）。

同时把两个 drawable 文件头注释里的「16dp 圆角」更新为「24dp 圆角（M6 需求 1）」。

**另需同步**：`widget/TodayWidgetContent.kt` 里课程行的 `cornerRadius(8.dp)` **保持 8dp 不变**（内层行圆角不跟着放大，否则与卡内边距比例失衡）。

### 3.2 为什么是 24dp

- 当前 16dp 在 168.3dp 高的卡上偏「方」；24dp 是 Material 3 大卡片的常见档位，与 App 内 `ImportChannelCard` 的 16dp、课程卡 4dp 形成清晰层级。
- 上限约束：卡高 168.3dp，圆角超过约 28dp 会让课程行内容贴到弧线上。24dp 留 4dp 安全边际。
- **不要**超过 28dp。

## 4. 需求 2 + 3：小组件跨天刷新与课后消除（**本次最重要**）

### 4.0 根因（已用 `dumpsys` 实测确证，不要改成别的）

**缺陷 2「第二天不刷新」根因**：`DailyWidgetRefreshWorker` 虽声明「首次延迟到下一个 00:05」，但实测它在系统 JobScheduler 里的状态是：

```
JOB androidx.work.systemjobscheduler:u0a470/28
  Trace tag: DailyWidgetRefreshWorker
  Minimum latency: +18h14m13s661ms
  Run time: earliest=+8h45m35s422ms        ← 实际要到次日 ≈07:33 才跑
  Required constraints: TIMING_DELAY FLEXIBILITY
```

即：**24h 周期任务的时间不是「首个 00:05」，而是被 WorkManager 按「入队时刻 + 24h」重排**，`setInitialDelay` 只影响首次；而首次实测落在 07:33（跨天刷新实际推迟 7.5 小时）。此外周期任务在 Doze 下还会继续漂移 —— **跨天这种"必须发生在凌晨"的语义用周期 Worker 表达本身就是错的**。

> 对照证据：`WorkSpec` 表里该 Worker `interval_duration=86400000`、`state=0`（ENQUEUED）、`schedule_requested_at=09-18 12:23:09`。同库另有 3 条 `androidx.glance.session.SessionWorker`（Glance 内部，**不是我们的任务**，别看错）。

**缺陷 3「课后不消除」根因**：结束闹钟的**唯一挂载点在 `TodayWidget.provideGlance` 尾部**（`TodayWidget.kt:93`）。而：

- 闹钟是**一次性** `setExactAndAllowWhileIdle`，App 被覆盖安装 / 强停 / 崩溃后 → 闹钟消失；
- 消失后**没有任何恢复路径**：`SystemEventReceiver` 只监听 `BOOT_COMPLETED / TIME_SET / TIMEZONE_CHANGED / 精确闹钟授权变化`，**不监听「应用被更新」**；`AppContainer.onDataChanged` 只刷新不重排（刷新会顺带排，但前提是有人调用刷新）；
- 实测 `dumpsys alarm` 里本包 8 条记录**全在 `Removal history`**，当前 pending 里没有 4002 闹钟 → 复现成立。

**本次修法**（两处都要改，缺一不可）：

### 4.1 【改】跨天刷新：WorkManager 周期任务 → AlarmManager 每日闹钟

**新增** `widget/DailyRefreshScheduler.kt`（新文件，约 70 行）：

```kotlin
/*
 * DailyRefreshScheduler.kt —— 小组件「跨天刷新」的精确闹钟（M6 需求 2）
 *
 * 为何弃用 WorkManager 周期任务：实测其 Job 的 earliest run time 落在次日 ≈07:33
 * 而非 00:05（周期任务时间按"入队时刻+24h"重排，且 Doze 下继续漂移）。
 * 跨天是"必须发生在凌晨"的语义，用 AlarmManager 精确闹钟表达才正确。
 *
 * 闹钟在每次触发后重排下一天（链式推进），并在 App 启动 / 系统事件后重排，
 * 保证覆盖安装、强停、重启后都能恢复。
 */
object DailyRefreshScheduler {

    /** 与提醒闹钟(4001)、结束刷新(4002) 不冲突的独立 requestCode。 */
    private const val REQUEST_CODE = 4003
    private const val REFRESH_HOUR = 0
    private const val REFRESH_MINUTE = 5

    /** 排定"下一个 00:05"的刷新；幂等（重复调用只覆盖同一 PendingIntent）。 */
    fun schedule(context: Context) {
        val appContext = context.applicationContext
        val alarmManager = appContext.getSystemService(AlarmManager::class.java)
        val triggerAt = nextRefreshEpochMilli()
        // 与 ReminderScheduler 同范式：优先精确，未授权则降级（不精确但可用）
        if (Build.VERSION.SDK_INT < 31 || alarmManager.canScheduleExactAlarms()) {
            alarmManager.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerAt, pendingIntent(appContext))
        } else {
            alarmManager.setAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerAt, pendingIntent(appContext))
        }
    }

    fun cancel(context: Context) { /* alarmManager.cancel(pendingIntent(...)) */ }

    /** 现在到下一个 00:05 的 epoch 毫秒（纯计算，抽成 internal 便于单测）。 */
    internal fun nextRefreshEpochMilli(now: LocalDateTime = LocalDateTime.now()): Long {
        val todayTarget = now.toLocalDate().atTime(REFRESH_HOUR, REFRESH_MINUTE)
        val target = if (now.isBefore(todayTarget)) todayTarget else todayTarget.plusDays(1)
        return target.atZone(ZoneId.systemDefault()).toInstant().toEpochMilli()
    }

    private fun pendingIntent(context: Context): PendingIntent {
        val intent = Intent(context, TodayWidgetReceiver::class.java).apply {
            action = AppWidgetManager.ACTION_APPWIDGET_UPDATE
            putExtra(AppWidgetManager.EXTRA_APPWIDGET_IDS,
                AppWidgetManager.getInstance(context).getAppWidgetIds(
                    ComponentName(context, TodayWidgetReceiver::class.java)))
        }
        return PendingIntent.getBroadcast(context, REQUEST_CODE, intent,
            PendingIntent.FLAG_IMMUTABLE or PendingIntent.FLAG_UPDATE_CURRENT)
    }
}
```

`nextRefreshEpochMilli` 的实现要求（**已抽成纯函数，必须单测**）：

| 入参 `now` | 期望返回值 |
|---|---|
| 当天 00:00:00 | **当天** 00:05 |
| 当天 00:04:59 | **当天** 00:05 |
| 当天 00:05:00（**边界：等于目标时刻**） | **次日** 00:05（`isBefore` 为 false → 走次日，避免"刚过就立刻又触发"） |
| 当天 12:00:00 | **次日** 00:05 |
| 当天 23:59:59 | **次日** 00:05 |

时区用 `ZoneId.systemDefault()`（与 `ReminderScheduler` 一致，勿用 UTC）。

**接线点（三处都要）**：

## 5. 需求 4 + 5：「正在上」标记（跨周误标 + 不实时）

### 5.0 根因

**缺陷 5（跨周误标记）**：`WeekGrid.kt:143` 是 `isToday = day == todayDow` —— **只比星期几**，没有「当前显示的周 == 当前真实周」这一层守卫。翻到上一/下一周时，同一天格的课照样被当成"今天"→ `isNow` 成立 → 画出 primary 边框。

对照：`DayHeader.kt:68-69` 有正确守卫 `weekContainsToday`（今天的日期方块就不会跨周误画）。**所以 WeekGrid 是漏了同一层守卫**，不是逻辑设计问题。

**缺陷 4（有时不标记）**：`TimetableScreen.kt:75-76` 的 `today` / `nowMinute` 在**每次重组时读一次快照**。若用户停留在周视图不动（无重组），跨过课程开始/结束时刻后**不会重算** → 边框不出现/不消失。这就是"有时候"。

### 5.1 【改】nowMinute 定时重算

**改 `ui/timetable/TimetableScreen.kt`**：把第 75-76 行的裸快照替换为**分钟级自动推进的状态**。

建议实现（放在 `TimetableScreen` 内、`Scaffold` 之前）：

```kotlin
// 每分钟推进一次的"当前时刻"（M6 需求 4）：
// 原来 LocalDate.now()/LocalTime.now() 只在重组时读一次，用户静置不动则跨过
// 上下课时刻后不会重算 —— 表现为"有时候不标记正在上的课"。
// 对齐到下一个整分钟边界再唤醒（不是固定 delay(60_000)），避免逐次累积漂移。
@Composable
private fun rememberMinuteTick(): Pair<LocalDate, Int> {
    var now by remember { mutableStateOf(LocalDateTime.now()) }
    LaunchedEffect(Unit) {
        while (true) {
            val current = LocalDateTime.now()
            // 对齐到"下一个整分钟"的毫秒数。实测语义（JDK java.time 直接验证）：
            //   12:00:00.000 → 60000ms   12:00:00.500 → 59500ms
            //   12:00:59.999 → 1ms       23:59:30     → 30000ms（跨午夜正确）
            val nextMinute = current.withSecond(0).withNano(0).plusMinutes(1)
            delay(Duration.between(current, nextMinute).toMillis())
            now = LocalDateTime.now()
        }
    }
    return now.toLocalDate() to (now.hour * 60 + now.minute)
}
```

然后 `val (today, nowMinute) = rememberMinuteTick()`。

**纪律**：
- 用 `LaunchedEffect(Unit)` + `while(true)` + `delay`（既有代码已在用 `kotlinx.coroutines.delay`，第 61 行有 import）；需补 `java.time.Duration`、`java.time.LocalDateTime`、`java.time.ZoneId` 的 import（`LocalDate`/`LocalTime` 已有，`LocalTime` 在本改动后可删）；
- **只在"下一个整分钟"唤醒**，不要 `delay(60_000)` 硬等（会累积漂移，且跨过整分钟时标记延迟可达 60 秒）；
- **不要**用 `while(true)` 里套 `withFrameNanos`（会每帧重组，与省电目标冲突）；
- 协程随 `TimetableScreen` 离开组合而自动取消（`LaunchedEffect(Unit)` 的标准语义），**无需手动 stop**；
- 与「减少动画」设置**无关**，不要受 `ANIMATOR_DURATION_SCALE` 影响。

> **关于 `AnimatedContent` 的相邻页**：`AppNav.kt:161` 的页面切换动画期间会短暂保留旧页，但
> 本定时器挂在 `TimetableScreen`（即 `AppScreen.Timetable` 目标页）内，随其离开组合即取消。
> 动画结束后 `TimetableScreen` 要么仍在组合（周视图→我的？不会，那是不同 AppScreen），
> 要么已被移除 → 定时器自然停。**不需要为它加额外的可见性判断**（勿过度设计）。

**性能影响（诚实评估）**：每 60 秒一次极小重组（只改 `today`/`nowMinute` 两个值）。本机帧率基线实测卡顿率 0.12%，此改动的影响量级远低于噪声，**但要按 §5.4 复测**。

**已知代价（如实记录，不遮掩）**：周视图**静置不动**时也会每 60 秒重组一次。在亮屏静置场景下这是必要代价
（否则"正在上"标记会停住）。若将来要省电，可改为「只在存在课程的时间段内运行」——
**本期不做**（属于过度优化，且需引入额外的可见性/时段判断）。

### 6.3 导入：走既有统一入口

**新增** `importer/file/JsonFileImporter.kt`（**照抄 `WakeupCsvImporter` 的形态**）：

```kotlin
class JsonFileImporter(
    private val repository: TimetableRepository,
) : ScheduleImporter {

    override val source: ImportSource = ImportSource.FILE_JSON

    override suspend fun import(payload: ImportPayload): ImportResult {
        val text = payload.text
        if (text.isNullOrBlank()) return ImportResult.Failure(ParseError.EmptyPayload, payload)
        return when (val r = ScheduleCodec.decodeToParsedSchedule(text)) {   // 见 §6.1
            is DecodeResult.Success -> ImportResult.NeedsConfirm(
                parsed = r.parsed,
                courseCount = r.parsed.courses.size,
                sessionCount = r.parsed.sessions.size,
                anomalies = r.parsed.anomalies,
            )
            is DecodeResult.Failure -> ImportResult.Failure(r.error, payload)
        }
    }

    override suspend fun commit(parsed: ParsedSchedule): ImportSummary =
        repository.applyImport(parsed)
}
```

**`ImportSource` 枚举新增 `FILE_JSON`**，并在 `CourseSource` 常量类新增：

```kotlin
/** 本 App 导出的课表文件 / 二维码导入（M6） */
const val FILE_JSON = "FILE_JSON"
```

**⚠️ 关键语义要求**：`applyImport` 会「按来源整体替换」（`deleteImportedByTermAndSource`）。因此：

- 同一个文件**重复导入两次**→ 第二次会替换掉第一次的，`replacedCount` 反映出来（这是既有语义，正确）；
- **不能**把 `source` 复用 `WEB` 或 `WAKEUP_CSV`，否则用文件导入会把教务导入的课表整体删掉——**这是数据丢失路径，必须避免**。

**`term` 的处理**：`ParsedSchedule.term` 要填上目标学期：
- 若文件里的 `term.startDate` 与当前激活学期**一致** → 填当前激活学期（走覆盖更新，正确）；
- 若**不一致** → 填 `null`，让 `applyImport` 回退到当前激活学期（**不要**自动新建学期——本期不做多学期管理，MVP 已明确排除）；
- 两种情况都在预览页显示提示：`anomalies` 里加一条 `"文件学期为「X」，将导入到当前学期「Y」"`。

`ScheduleCodec.decodeToParsedSchedule` 返回 `DecodeResult`（自定义 sealed：`Success(parsed, ...)` / `Failure(ParseError)`）。

**⚠️ 不要新增 `ParseError` 子类**（原稿曾建议新增 `MalformedJson` / `WrongApp` / `UnsupportedVersion`，**已撤销**）。理由（实测）：

- `ParseError` 定义在 `parser/api/ScheduleParseResult.kt:28`，是 **sealed interface**，只有 3 个子类：

- 全项目有 **两处穷举 `when`（无 `else` 分支）**：`ImportHubViewModel.kt:118-122` 与

## 7. 需求 6-B：二维码导出 / 导入

### 7.1 可行性（已实测，**方案已定，不要改**）

用真机课表（9 门课 / 16 条 session）实测三种编码：

| 方案 | JSON | deflate | base64 |
|---|---|---|---|
| 扁平全字段 | 1511 | 577 | **772** |
| 嵌套去重 | 1009 | 554 | **740** |
| 列式数组 | 1296 | 563 | **752** |

放大到 64 条 session（≈4 倍）：base64 仅 **832~836 字节**（deflate 对重复结构压缩率极高）。

QR 版本容量（byte 模式，M 级）：版本 25 = **1000 字节**；版本 30 = 1370；版本 35 = 1812；版本 40 = 2331。

**结论：单张二维码可行**。真机课表（740-772 字节）落在版本 25（M 级 1000 字节）；放大 4 倍（836 字节）仍在版本 25。**留 5% 余量后版本 25 可承载到约 950 字节。**

**方案**：`deflate(level 9) → base64 → 二维码`，**单码**。载荷形如 `XPUTT1:<base64>`（前缀 7 字节，见 §7.3）。

- 真机课表 772 字节 + 前缀 7 = **779 字节** → 版本 25（M 级 1000）**仍有余量**，结论不变。
- 超过 **2000 字节**时**不做分片**（分片扫码体验很差，MVP 不做）→ 生成前检查，超限则提示「课表较大，请改用导出文件分享」。**2000 是含前缀后的总长**。
